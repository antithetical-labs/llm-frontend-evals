How a session runs

Three surfaces, one timeline, all in sync.

  1. 00:00 · broadcaster

    Point Streamforge at your editor

    The desktop agent captures your assistant transcript and your git working tree. It never uploads a file your .forgeignore excludes.

  2. 00:00 → live · viewer

    Read the prompt before the code lands

    Prompt, model response and diff share a single scrubber. Rewind to any moment and the three panes move together.

  3. any timestamp · anyone

    Fork the repo at that exact frame

    Every message boundary is a real commit. Fork mid-session, keep the transcript as history, and take the branch somewhere else.

Built for people who actually ship

What you get that a screen recording can't give you.

01 · transcript

The prompt log is a first-class artifact

Every message is indexed, searchable and quotable. Find the exact wording that got a stubborn refactor to land, then cite it with a timestamped permalink.

  • full-text search across 1.2M sessions
  • model, temperature and tool calls shown inline
  • secrets redacted before they leave the machine

02 · fork

One command, mid-stream

Take the repository as it stood at any second of the broadcast, transcript attached as commit notes.

$ forge fork rk_builds/limiter --at 02:14:07
  • real git, no lock-in
  • upstream diff kept alive after the stream ends

03 · review

Comment on a line, not a chat box

Viewers annotate the diff while it is still warm. The broadcaster sees threads pinned to the code, not scrolling past it.

  • line-anchored threads survive rebases
  • resolved notes export as a review summary
