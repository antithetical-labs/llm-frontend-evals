How it works

Three moves, in order, from your terminal to someone else's checkout.

01

Attach the agent

Point the Streamforge CLI at your session. It captures the prompt channel, the model response, and the diff the editor actually wrote. Nothing is reconstructed after the fact.

02

Broadcast the loop

Viewers see the three tracks side by side and can scrub back to any prompt. Secrets, env files, and paths you exclude never leave the machine.

03

Hand over the repo

Every commit the stream produces is a fork point. A viewer takes the tree, the prompt history, and the test run, then keeps going in their own branch.

What you get

Built for people who read diffs for a living.

F.01

Fork at any frame

Pause on the commit you care about and take it. You get the working tree, the branch, and the exact prompt sequence that produced it, so the reasoning ships with the code instead of dying in a chat window. forge fork rieko/rate-limiter@7f1c9ad

F.02

The prompt log is source

Prompts are stored alongside the tree in .forge/prompts.jsonl, addressed by commit. Grep it, diff it, replay it against a different model, or review it like any other file in the pull request.

F.03

Discovery by stack, not by thumbnail

Follow a language, a framework, a failing test suite, or one builder. Streams surface by what is open in the editor and what the last test run said, so a Rust borrow-checker fight never lands next to a reaction video.
