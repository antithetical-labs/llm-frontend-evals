Acid design is confrontational, synthetic, and intentionally over-stimulated. It borrows from rave flyers, early web graphics, cyberpunk interfaces, terminal culture, glitch art, industrial signage, and late-1990s/early-2000s digital ephemera. For Streamforge, the result should feel less like a polished SaaS dashboard and more like a live transmission from an experimental development environment: fast, technical, participatory, and slightly unstable.

**Palette:** Start with a near-black or ink-black foundation rather than neutral corporate gray. Layer highly saturated “toxic” colors over it—acid lime, ultraviolet, electric cyan, hot magenta, and signal orange. These colors should behave like emitted light: sharp borders, luminous accents, selective glows, and occasional clashing combinations. Off-white can support readable body copy, but pure white should be used sparingly. Color should communicate state as well as mood: lime for live activity and successful builds, magenta or orange for interaction, cyan for code and model output. Avoid soft gradients, tasteful pastels, and the ubiquitous blue-purple SaaS wash. If gradients appear, they should feel artificial and compressed, like thermal imaging or a corrupted display.

**Typography:** The typographic system should pair an expressive, condensed or extended display face with a practical monospaced face. Headlines can be oversized, tightly tracked, aggressively wrapped, and occasionally italicized or outlined. Supporting text, metadata, prompts, timestamps, branch names, and interface labels should use monospace to reinforce the developer context. Hierarchy should come from dramatic jumps in scale rather than many subtle font weights. Uppercase labels, square brackets, slashes, arrows, underscores, and command-line syntax can become part of the visual language. The design should reject friendly geometric SaaS typography, soft rounded lettering, and generic center-aligned motivational copy.

**Texture:** Acid design should not look clinically flat. Appropriate textures include CRT scan lines, fine pixel grids, halftones, dithering, chromatic aberration, digital noise, rough photocopy artifacts, cursor trails, waveform traces, and deliberately imperfect registration. These should create atmosphere without obscuring code or essential controls. Glows should be localized and hard-edged rather than turning every object into a blurry neon cloud. Thin technical rules, coordinate marks, build logs, and subtle compression artifacts can make the page feel captured from a live system.

**Layout logic:** The layout should feel modular, dense, and in motion. Use an underlying grid, but permit elements to interrupt it: oversized type crossing columns, status markers attached to card edges, vertical labels, cropped windows, asymmetrical gutters, and layered panels. The hero should quickly demonstrate the product rather than relying on an abstract illustration—ideally through a staged live-stream interface showing the developer, prompt exchange, generated output, evolving code, viewer activity, and a prominent repository-fork action. Sections can resemble channels, terminal panes, or broadcast modules. Strong borders and visible divisions are preferable to floating rounded cards. Motion can come from marquees, blinking live indicators, scrolling logs, shifting waveforms, and small reactive highlights, but the core reading path must remain obvious.

**UI shape and imagery:** Favor rectangular frames, clipped corners, tabbed panels, hard shadows, crosshairs, badges, and exposed interface chrome. Photography, if used, should appear as a live feed rather than lifestyle imagery. Product screenshots and code are the primary imagery. Icons should be simple, technical, and legible—closer to symbols on equipment than decorative illustrations. Rounded pills should be reserved for genuine status indicators, not applied to every label and button.

**Tone:** The voice should be direct, technically literate, and active. It should speak to working developers without explaining what repositories, prompts, branches, or build logs are. Messaging should emphasize watching decisions happen, learning from real workflows, and turning observation into action by forking the exact state of a project. Labels such as `LIVE`, `PROMPT IN`, `MODEL OUT`, `BUILD PASS`, and `FORK @ HEAD` can blend product meaning with the aesthetic.

**What it borrows:** Acid design borrows rave culture’s fluorescent urgency, brutalism’s exposed structure, cyberpunk’s machine-human tension, terminal interfaces’ density, and early web design’s willingness to be strange. It also uses broadcast graphics—lower thirds, timestamps, signal bars, channel identifiers—to make live activity tangible.

**What it rejects:** It rejects frictionless corporate minimalism, spacious beige branding, generic gradient blobs, excessive rounded cards, polished stock photography, ornamental 3D mascots, and vague claims about “supercharging creativity.” It should also avoid becoming a parody of hacker culture: no meaningless green code rain, fake security warnings, or illegible glitch effects. The design can feel volatile, but the product proposition, navigation, live content, and fork action must remain immediately understandable.
