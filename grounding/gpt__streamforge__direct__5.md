## Aesthetic Direction: Acid Software Broadcast

Streamforge should feel like a live development environment pushed into broadcast mode: technical, volatile, and visibly in motion. The visual language draws from acid graphics, early web experimentation, rave flyers, terminal interfaces, and contemporary developer tooling—but avoids becoming a nostalgic Y2K pastiche or a generic neon cyberpunk site.

### Palette

The foundation is nearly black, with subtle blue or violet undertones rather than neutral charcoal. This gives code, video, and interface chrome a dark-stage environment. Over it, use a limited set of electrically saturated colors: toxic lime, ultraviolet, hot magenta, and occasional signal cyan. These should behave like system states and emitted light—not decorative rainbow gradients.

Acid lime should be the primary action color, used for live indicators, calls to action, active tabs, and repository-fork moments. Violet and magenta can distinguish AI output or model activity, while cyan can mark developer input and code changes. White should be cold and slightly tinted, reserved for essential text. Muted copy should remain legible rather than collapsing into low-contrast gray.

Gradients should feel synthetic and abrupt: concentrated glows, color bands, iridescent edges, or posterized transitions. Avoid soft “friendly SaaS” gradients.

### Typography

The typography should combine a condensed or extended grotesk display face with a precise monospace. Headlines should feel compressed, loud, and editorial—more like a release poster or a broadcast title card than a startup pitch deck. Uppercase, tight line spacing, oversized scale, and selective outline or italic treatments can create velocity.

Monospace type carries functional information: prompts, model names, branch names, viewer counts, timestamps, terminal output, and stream metadata. It should not be used everywhere; the contrast between expressive display type and utilitarian monospace is central to the identity.

Typography can be cropped, stacked, repeated, or allowed to collide with interface elements, but body copy must remain clean and comfortable for working developers. The energy belongs in hierarchy and composition, not at the expense of reading.

### Texture and Image Treatment

The surface should feel digital rather than polished: scan lines, halftone fields, low-opacity noise, dithered gradients, pixel grids, waveform traces, cursor artifacts, and occasional compression glitches. These textures should suggest transmission, rendering, and machine activity.

Code and prompts are the primary imagery. Instead of relying on generic photos of developers, the page should show layered stream interfaces: a camera feed, prompt history, model response, editor diffs, terminal output, and repository state. Screenshots can be treated as broadcast signals—with colored borders, offset shadows, clipped corners, and small diagnostic labels.

Glitch effects should be static or restrained. Constant distortion would undermine trust and make the product feel unstable. The platform is high-energy; the interface itself must still feel reliable.

### Layout Logic

The layout should use a strong technical grid, then visibly break it. Large editorial headlines can span columns while stream cards, prompt panels, and code windows overlap or sit slightly off-axis. Thin rules, coordinate labels, numbered sections, and alignment markers make the page feel engineered even when the composition is aggressive.

Sections should alternate between dense information clusters and areas of hard negative space. The hero should resemble an active control room rather than a centered headline floating above a browser mockup. The key product loop—watch, inspect, fork—should be apparent immediately and repeated as a visual sequence throughout the page.

Cards should feel like modules in a system: sharp edges, narrow borders, hard shadows, status lights, and visible metadata. Rounded corners should be rare and small. Motion can include ticker-like marquees, blinking live states, streaming text, diff highlights, and panels that snap into place rather than float gently.

### What It Borrows From

The direction borrows from:

- Acid-house and rave-flyer graphics: fluorescent color, compressed type, repetition, urgency, and anti-corporate energy.
- Early web and net-art aesthetics: exposed grids, browser artifacts, pixel texture, and deliberate visual friction.
- Terminal and IDE interfaces: monospace labels, syntax color, panes, diffs, logs, and keyboard-driven precision.
- Broadcast graphics: live bugs, lower thirds, timestamps, signal indicators, and layered information.
- Brutalist editorial design: oversized hierarchy, hard borders, asymmetric composition, and direct language.
- Generative and machine-made visuals: procedural grids, noisy gradients, token streams, and model-state patterns.

### What It Rejects

It rejects the familiar AI-startup formula: soft purple gradients, floating glass cards, glowing orb mascots, vague claims about “supercharging creativity,” and anonymous stock illustrations. It should not look like a crypto exchange, a gaming peripheral brand, or a cyberpunk movie interface.

It also rejects illegibility for its own sake. Acid design can be abrasive, but Streamforge serves experienced developers who need to understand the product quickly. Code must look authentic, metadata must be scannable, and the primary actions must remain obvious.

The result should feel experimental but competent: a place where software creation is treated as a live cultural event, without disguising the technical reality of prompts, output, commits, and forks.
